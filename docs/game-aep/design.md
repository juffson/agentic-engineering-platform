# Game AEP 设计提案

建议基于 AEP 维护一个可独立安装、独立升级的游戏工程工具。游戏团队从某条需求出发，能看到它改动了哪些游戏内容、应该在哪些环境验证、每条验收实际观察到了什么。第一个接入项目是 PokeOriginal。本分支交付设计，实施从下文 M1 开始。

## 复用边界与仓库分工

基线为 AEP `096af830d0b56d8b1f7807e7cac47688e184aa80`。[任务解析与派发](../../src/git.rs)已支持指定 Git remote、把任务固定到提交，并逐文件核对候选改动范围。[执行器](../../src/run.rs)在独立 worktree 对同一候选运行一条参数数组形式的 `check`，写日志、候选 SHA、退出码和本地证据。[进程适配](../../src/agent.rs)使用 Unix 进程组；现有 CLI 面向 Linux/macOS，Studio 的交付入口在 macOS。Gitea 可作为 Git remote，issue、PR、附件与状态回写另需接口。SQLite 记忆在同一克隆的 worktree 间共享。

| 归属 | 建议承载的职责 | 首版接口 |
|---|---|---|
| AEP 核心 | 固定规格版本、派发、隔离工作区、候选提交、精确文件许可、运行锁、基础证据 | 继续接受现有的 [task.json](../../specs/market-volume-dedup-rust/task.json)。行情示例与既有任务可照常运行。 |
| Game AEP 工具仓库 | 发布与核心版本兼容的命令行工具；根据规则规划检查、探测能力、执行阶段、导出证据；维护 Gitea 适配及测试夹具 | 首期增加独立子命令程序 `game-aep`。作为已安装的可信程序接受旧 `check` 的单次调用，内部调多个阶段。后续再按实际需求给 Studio 加证据视图。 |
| 游戏仓库 | 维护模块规格、源数据、生成器、测试、发布脚本；评审本项目的路径与检查映射、设备要求、验收阈值和运行参数 | 建议新增 `.game-aep/profile.toml`；每个派发任务的 `specs/<task>/spec.md` 只列冻结的验收和现有领域文档引用，旁边的 `task.json` 声明可改文件。 |
| 执行环境与维护者 | Linux/macOS 做首批自动化；Windows 工作机可编辑和审查；需要原生 PC 操作、移动设备或人工美术判断的任务由对应环境补证 | 首版单机运行、手工导入跨设备证据。设备注册、自动调度和原生 Windows 进程回收留待后续里程碑。 |

游戏源码始终在游戏 worktree 内执行。工具仓库可以用合成地图、合成表格和测试 Git remote 开发；地区原始素材、玩家存档、运营凭据及签名材料留在获准持有它们的环境。上游更新时以 AEP 原有测试和游戏适配契约做兼容性检查。

## 一次任务如何流转

1. **冻结需求。** 在 issue 确定玩家行为、适用地区/端、失败与恢复条件，为验收编号。规格提交引用经评审的游戏 profile 和工具版本。生成物的具体路径也要出现在 `allowed_paths` 中；发现新影响面就修订规格并按 AEP 规则换任务 ID。
2. **规划。** 在游戏克隆中使用配置的 remote。取规格 SHA 到候选 SHA 的完整差异，包含增删和重命名两端；路径规则与任务显式标注的业务影响取并集。联机协议、双端 UI 等可跨目录传播。每个入选阶段输出触发原因、AC、前置能力和运行入口。无法归类的文件标为待判定，交维护者补映射。
3. **预检。** 核对引擎/工具版本、LFS 实体、地区数据版本、可用数据库与设备。为每次运行分配临时库、存档、端口和输出目录；独占设备领取互斥锁。多 worktree 下用显式上游路径解析地图源。预检结果区分环境缺失和游戏行为失败。
4. **执行与恢复。** 先跑低成本静态检查，再跑相关数据、运行时和设备阶段；不同夹具可以并行，共用导出器或设备的阶段串行。前置失败时保留依赖关系并停止受影响阶段。超时或中断回收所属进程，保留已写的日志；重试换 attempt、重新准备夹具，并关联前一次结果。
5. **审查。** 按 AC 汇总通过、失败、阻塞、待人工、明确不适用及原因。必需项齐备后才能报告验收通过。Gitea 适配器用“仓库 + PR + 候选 SHA”标识报告，重试更新同一报告；回写前重新读取 PR head。遇到新提交就将旧报告保留为历史，基于新 head 重验。离线时先导出 Markdown，再补传。
6. **交付。** PR 作者或维护者审查差异和证据后决定合入。发布操作沿用游戏的独立工作流和权限；平台记录已交付的构建、版本与发布回执。没有发布回执时，交付状态停在已合入。

### 任务规划表（首个项目适配）

| 变更信号 | 依次执行或采集的内容 | 判定要点 |
|---|---|---|
| 文档、规格、操作说明 | 校验路径和引用；对变更的验收条款做需求审查 | 纯文档可结束于审查；文档同时声明玩法变化时，显式标明对应实现任务。 |
| 策划表、迁移、地区脚本 | 以地区源码版本和表中业务键定位改动；生成字段级差异，定点再生；跑服务端守门、旧库升级和所需数据库用例 | 相同输入重复生成的语义结果一致；明确新增、删除和变更行；已应用迁移字节保持一致。新增编号与目标分支冲突时重新规划。 |
| 地图、碰撞、动画、音频或 UI 资源 | 检查源素材版本、导入设置、LFS 对象、UID/路径；选择地图/客户端现有守门；在固定地图、坐标、时间点采基线和候选画面，音频记录播放事件与人工试听 | 地图验证碰撞、分层、传送和动画；UI 验目标分辨率、中文字体和遮挡；美术或听感需要人工签认时附对应样本。 |
| 客户端脚本、交互或剧情 | 客户端静态守门 → Godot 启动及全脚本/场景冒烟 → 从 MCP 目录选玩家操作用例 → 任务要求的实体设备检查 | 为每项注明输入层级（动作注入、按钮事件、设备输入）、地图、初始角色状态和终态。剧情覆盖相关地区、性别和重新登录恢复。 |
| 服务端、协议、多人状态 | Rust 构建与定向单测、服务端守门；SQL 变更跑两种数据库；协议变更追加协议走查与匹配版本的 Godot 客户端，多人用独立角色 | 记录消息版本和双方状态；资产发放、交易或战斗结算应覆盖重发、断线、回滚，必要时测试旧端。 |
| 打包、热更、性能敏感场景 | 区分桌面与安卓基线，测试环境从指定旧版升级并冷启动；性能任务在同机型、场景、采样窗口下对照基线 | 记录构建标识、补丁大小、资源加载与恢复结果；帧时间、内存、包体阈值按项目规格确定，缺基线时报告原始值。 |

### 如何对接现有执行器

首个试点使用已有候选的 `aep run --candidate ...`。当前实现代理路径会先 `git add -A`，再检查文件范围，与游戏仓库要求逐文件暂存及其 LFS 工作流冲突。接入自动实现前，先按允许清单暂存改动并拒绝清单外的新增、删除和修改，再建立候选提交；用包含未跟踪导入文件的夹具验证。

建议的 `check` 形如 `["game-aep", "verify", "--task", "world-input"]`，这是待开发的接口。AEP 当前只传工作目录和 argv。M1 由启动端在派发时解析并固定规格 SHA、候选 SHA 和唯一证据目录，通过受控环境传入；校验器比对实际 HEAD，并从规格提交读取 profile。生成的附件要在 worktree 清理前写到工作区外。现有 `evidence.json` 仍由 AEP 独占写入；Game AEP 输出独立报告，启动端通过 run ID 和双方记录的 SHA 对齐两个报告。游戏阶段失败返回非零，并在独立报告内写明失败或缺设备。

### 证据和权限契约

| 记录 | 必需字段与用途 |
|---|---|
| 运行身份 | 报告版本、游戏仓库身份、issue/PR、run ID 与 attempt、规格/候选 SHA、profile 和工具版本。跨设备导入还要匹配本次计划摘要；校验失败显示具体不匹配字段。 |
| 阶段和产物 | 阶段 ID、关联 AC、触发原因、执行机能力、命令参数、相关工具/素材版本、夹具、起止时间、退出码、判定和失败位置。图片、日志、表差异用相对路径、大小和 SHA-256 引用。 |
| 人工与发布 | 人工证据记录验证者、设备、系统、游戏构建摘要、操作步骤、观察结果；发布另记平台、基线、产物摘要与回执。共用同个 SHA 的不同导出构建要分别记录。 |

执行器在只含测试资源的工作区运行候选代码，检查策略和命令清单来自已评审版本。凭据由独立的回写端持有，仅上传脱敏摘要和获准附件；私有大文件保留在项目证据存储。游戏内容的所有者可设置附件保留期。模型交接只传允许的摘要；共享记忆可解释历史决定，最终规则仍链接已评审规格。

## 第一个试点：野外方向输入

选择已有实现和可观察终态的小功能，可先检验平台是否选对用例。示例基于 `client/gd/world/DirectionInput.gd` 和 `test/mcp/mcp_runtime_direction_last_input.py`。用例向运行中的 Godot 注入方向动作，检查玩家朝向和坐标。建议建独立的合成回归候选，在受控工作区临时恢复旧优先级，作为必败对照。

| 验收 | 环境与操作 | 必要证据 |
|---|---|---|
| AC-1 客户端能加载 | 在候选上执行场景冒烟，记录 Godot 精确版本 | 脚本/场景检查计数、失败项、日志。 |
| AC-2 后按优先且释放恢复 | 测试服、固定角色与空地。按住上，再按下，再松下；同时覆盖上＋右。运行已有方向用例。 | 每步的预期/实际朝向和位移。旧优先级候选在第二步失败，同规格修复候选通过。 |
| AC-3 手机输入到移动的整条链生效 | 若任务涉及触屏，在同一候选导出的安卓构建上通过实际控件操作，再测试松手停止、打开菜单后的焦点和返回世界；PC 端用实体键盘复验相应按键。 | 分别记录机型、构建摘要、输入方式、步骤与终态。动作注入仅支持 AC-2；未拿到设备时 AC-3 保持待验。 |

PR 摘要首先展示每条 AC 的状态，再链接完整报告。譬如 AC-1、AC-2 已通过而 AC-3 缺设备，就显示“2/3 已验证，待安卓和 PC 输入复验”，并列出需要补的操作。这样策划可以直接判断缺哪项体验证据。

## 实施顺序与退出条件

| 里程碑 | 建议改动位置及交付 | 完成判据 |
|---|---|---|
| M1 单机只读验收 | 在工具仓实现规划、能力探测和报告导出，用合成 Git 仓与最小 profile 测试。随后在游戏侧用已评审的方向输入任务接入候选模式。 | 通过与必败对照各一次；缺 Godot 准确标为阻塞；一次重复派发可读回原证据；成功清理 worktree 后仍能读附件。 |
| M2 内容生产 | 在游戏 profile 加入地区数据、表格、地图和资源规则；在工具侧支持语义差异与产物摘要。选一次地图或剧情变更跑全链。 | 一处表格变化能定位单元格对应的业务键；漏迁移、错误地区来源或缺 LFS 实体能被对应检查检出；同输入重跑得到一致结果。 |
| M3 联机与跨端 | 接入双数据库、Godot 世界场景、双客户端和人工设备证据，加入 Gitea PR 回写。 | 模拟断线重试后数据正确；设备证据一旦候选或构建变化即失效；同一候选重试只产生一份最新 PR 摘要，并能查到历史。 |
| M4 发布与反馈 | 对接现有发布工作流的只读结果和性能对比，在测试环境演练桌面/安卓各自的升级恢复。 | 一次指定旧版可升级至对应候选，错误基线可定位；从回执反查候选与验证记录，从版本关联至少一条脱敏反馈。 |

建议先用 M1 衡量实际收益：记录人工选用例和整理 PR 证据耗时、漏选的验收项、设备阻塞次数及误报。依据试点数据决定是否投资跨机调度和 Studio 界面。现有入口的核对依据见[游戏工具流程清单](pokeoriginal-workflow.md)。

# 事项与远端联动：开启和交付

## 1. 背景

今天一个事项从开启到交付都只在本机：

- **开启**：第一个阶段用 `git worktree add -b aep-stage/<id> … HEAD` 建事项分支，起点是主工作区当时检出的分支。PokeOriginal 的 PR#1926 事项就是从一个没推送的 `rebase/code-structure-review` 分出来的，交付时带上了 22 个不属于事项的提交，而且落后 `gitea/dev` 66 个提交、7 个文件冲突。
- **跟随基线**：`align_base` 把「主工作区当前检出的分支」当作基线，同样依赖用户此刻检出的是什么。
- **交付**：只有本地快进合并（`merge.rs`），合进一个本地分支。团队实际的流程是把分支推到远端、提 PR 到 `dev`，在 Gitea / GitHub / GitLab 上评审合并。

## 2. 目标

1. 事项从**确定的基线**开启：项目给每个仓库配置「目标分支」（如 `dev`）和「远端」（如 `gitea`）。开启时先 fetch 远端，再从 `<远端>/<目标>` 建分支，与用户当前检出了什么无关。
2. 阶段之间**跟随远端基线**：`align_base` 以 `<远端>/<目标>` 为基线，并先 fetch。规则不变：开发、测试前自动合入；冲突交给开发；验收、交付发现基线前进就退回。
3. **交付推到远端并提 PR**：确认交付时做三件事：
   - 推送事项分支（`<前缀><事项短名>`）；
   - 提 PR 到目标分支；
   - 在事项上记下 PR 的地址和编号。

   之后 Studio 跟踪 PR 状态（打开 / 已合并 / 已关闭）。PR 合并后，事项显示「已合并」，可以清理工作区。
4. **已有 PR 的事项**（例如在 PR#1926 上继续做）：可以绑定一个已有 PR。交付时更新该 PR 的源分支，用 `--force-with-lease` 指向上次看到的提交，不新开 PR。

## 3. 不做

- 不自动合并 PR，评审和合并仍然在代码平台上完成。
- 不自动处理 PR 上的评审意见。以后可以把它当作「继续对话」，接回开发阶段。

## 4. 配置（项目 · 仓库）

```jsonc
// Project.remotes[<仓库路径>]
{
  "remote": "gitea",          // 默认：目标分支的 upstream 所在远端，没有则用 origin
  "target": "dev",            // 默认：远端 HEAD 指向的分支
  "delivery": "pull_request", // "local" | "pull_request"
  "branch_prefix": "aep/",
  "pr": "auto"                // "auto" | "api" | "agit" | "manual"
}
```

- 项目没有为某个仓库配置时，行为与现在相同：本地合并，基线取主工作区 HEAD。这样旧项目不受影响。
- Studio 的「仓库」页给每个仓库加一张「远端与交付」卡片。卡片显示探测到的默认值，可以修改。

## 5. 开启

`workflow_stage::workspace` 第一次建工作区时，如果仓库有远端配置：

1. 运行 `git fetch <remote> <target>`。fetch 失败时，以事项失败结束，并说明原因（网络、权限），不回退到本地 HEAD。
2. 运行 `git worktree add -b aep-stage/<id> <path> refs/remotes/<remote>/<target>`。
3. 在 evidence 里写 `base: {remote, target, sha}`，作为事项的起点。

从已有分支导入的事项（prepared）和绑定了 PR 的事项，继续检出原来的分支。

## 6. 跟随基线

`align_base` 的基线解析：

- 有远端配置时，先运行 `git fetch <remote> <target>`，基线取 `refs/remotes/<remote>/<target>`。fetch 失败只写入 evidence，基线退回到上次 fetch 的结果，阶段不因此失败。
- 没有远端配置时，保持现在的做法，基线取主工作区检出的分支。

其余逻辑不变。冲突时：平台先开始合并，开发阶段只改带冲突标记的文件，平台随阶段一起提交。

## 7. 交付：推送并提 PR

交付面板里，「查看 Diff 并合入」在 `delivery = pull_request` 时换成「推送并提 PR」。

### 7.1 预览（只读）

- fetch 远端目标分支。
- 核对已验收的提交是否包含 `<remote>/<target>`。不包含时：
  - 没有冲突：提示「目标分支前进了 N 个提交」，并给出「退回测试」按钮。
  - 有冲突：给出「退回开发」按钮。
- 显示将要推送的分支名，以及 PR 的标题和描述，都可以编辑。
  - 标题默认取 `事项名`。
  - 描述由需求摘要、验收结论和交付归档的 AEP-HANDOFF 拼成，并附上本事项各阶段的提交列表。

### 7.2 确认

1. 推送：`git push <remote> <已验收提交>:refs/heads/<分支>`。
   - 新分支不加 force。
   - 绑定了已有 PR 时，用 `--force-with-lease=<分支>:<上次记录的 sha>`。
2. 提 PR，按优先级：
   1. **api**：插件里有这个主机的令牌时，调用 GitHub / GitLab / Gitea 的 API 创建 PR。令牌按主机绑定，见插件事项。
   2. **agit**：Gitea / Forgejo 支持。运行 `git push <remote> <提交>:refs/for/<target>/<topic> -o title=… -o description=…`，不需要令牌。
   3. **manual**：只推送分支，返回网页上的「创建 PR」链接（compare URL）。

   `auto` 按 api → agit → manual 依次尝试。哪一步成功就记哪一种。
3. 在交付记录上写 `pr: {remote, branch, number?, url?, mode, pushed_sha, at}`。事项显示「已提 PR #N」。

### 7.3 跟踪

`plugins.rs` 的远端刷新顺带读取事项 PR 的状态。PR 合并后：

- 交付记录标为 `merged: {target, sha, at, via: "pr"}`；
- 侧栏把事项移到「已合并」；
- 允许清理工作区和本地分支，远端分支由代码平台删除。

### 7.4 交付后跟进（已交付 → 合并 → 发布 → 效果）

「已交付」不是终点。一个事项提交 PR 之后，还要经过评审、合并、发布，最后要看改动有没有达到目的。设计上把这段路做成事项上的「跟进」阶段组。它跟在交付归档之后，事项仍然留在「已交付」分组里，并标出所处的子状态：

| 子状态 | 怎么知道 | 自动动作 |
|---|---|---|
| PR 待评审 | 7.3 的 PR 状态 | 没有 |
| 有评审意见 | 插件远端刷新时读到新的评审评论 | 提示「从开发阶段继续」：开一个开发阶段的继续对话，意见作为本轮说明，沿用原会话；改完再走测试 → 验收 → 推送更新，PR 会自动跟随 |
| 已合并 | PR 状态为 merged，或者目标分支包含已推送的提交 | 写入 `merged`，允许清理 |
| 已发布 | 某个发布标签（tag）或发布分支包含合并提交。项目可配置标签规则，如 `v*` | 记下首个包含它的版本和时间 |
| 效果评估 | 发布后经过 N 天，或手动触发 | 运行一个「效果评估」阶段，只读：对照需求里的验收和指标，读取日志、指标和 issue（通过插件或命令），写出结论；需要返工时用 AEP-BACK 开新一轮 |

- 「从上一个阶段继续跟进」直接复用现有机制：继续对话（follow-up）加会话复用。评审意见会作为说明带进去。
- 跟进阶段是流程里可以配置的尾部阶段。内置流程默认只带 PR 跟踪和合并 / 发布识别，效果评估默认关闭，按项目开启。
- 侧栏「已交付」分组下，每个事项显示子状态：「PR #N 待评审 / 有 2 条意见 / 已合并 / 已发布 v1.4 / 已评估」。

## 8. 失败与安全

- 推送和提 PR 都是对外操作，只在用户点「确认」后执行。自动运行不会推送。
- 推送失败（被拒、需要 rebase）时，不改动交付记录，并显示 git 的原始错误。
- `--force-with-lease` 失败，说明有人改动过远端分支。这时提示先 fetch 并核对，不重试 force。
- 令牌只经过 stdin / 钥匙串，见插件事项的令牌规则。agit 和 manual 模式不需要令牌。

## 9. 分期

| 期 | 内容 |
|---|---|
| 1 | 远端配置（探测默认值）；从远端目标分支开启；`align_base` 跟随远端；交付「推送并提 PR」，支持 agit 和 manual，记录 PR；CLI `aep project deliver-pr` |
| 2 | api 模式（GitHub / GitLab / Gitea），基于插件事项的 forge 层，Gitea 需要新增 provider；PR 状态跟踪和「已合并」；已交付分组显示子状态 |
| 3 | 交付后跟进（7.4）：评审意见从开发阶段继续，合并 / 发布识别，效果评估阶段 |
| 4 | 从 issue 开启事项，issue 正文作为 brief |

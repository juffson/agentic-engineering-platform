# PRD：可编排的阶段流程

事项：工作流 · 可编排的阶段流程（work-1e54b2e4e4f647659b819af873e2461c）
阶段：产品需求 · 2026-11-24

## 1. 背景与目标

今天每个事项只能选三套内置模板之一（`src/workflow.rs` 的 `Template::{Legacy, Software, Game}`），阶段是写死的静态数组。调度、自动运行、交接、归档、合并、Studio 都直接用 `template.stages()[i]` 和阶段下标，没有别的流程来源。

目标：

- G1：抽象出「流程定义」，作为阶段列表的唯一来源。三套内置模板改用它表达，行为不变。
- G2：项目可以定义自己的流程（增删、重排、改名阶段，改说明、角色、能否跳过、退回目标），新事项可以选用。
- G3：已有事项、历史执行记录和归档照常打开、继续推进，不需要迁移操作。

## 3. 待确认问题与本 PRD 采用的默认答案

本阶段无法当面确认。下表给出建议答案，后续阶段按此推进；负责人如不同意，在本阶段退回时改这里即可。

| # | 问题 | 采用的答案（假设） | 理由 |
|---|---|---|---|
| Q1 | 「可编排」指什么 | **项目级自定义流程**：在项目里增删、重排、改名阶段，改说明/角色/跳过/退回。事项创建时选一套流程；**不做**事项级临时增删阶段（已有的 AEP-SKIP、人工跳过、退回已覆盖临时调整）。 | 范围可控，覆盖「去掉交互设计、加审查阶段」这类诉求 |
| Q2 | 定义存在哪里 | **Studio 项目数据**（与项目其他设置同处），不放在仓库文件。 | 一个项目可以关联多个仓库；放仓库会产生「以哪个仓库为准」的问题 |
| Q3 | 并行 / 条件跳转 | **不支持**。流程是线性阶段列表；条件只通过已有的 AEP-SKIP / AEP-BACK 表达。 | 与「不做」一致 |
| Q4 | 进行中事项改模板 | **事项创建时冻结一份流程快照**。之后改动或删除项目流程，不影响已创建事项；已有事项没有快照，按其 `template` 解析到内置模板。本期不提供「把进行中事项切换到新流程」。 | 下标在事项内保持稳定，`profiles/budgets/attempts` 等按下标的数据不需要迁移 |
| Q5 | Studio 编辑界面 | **需要一个表单式编辑器**（列表 + 上移/下移/添加/删除 + 字段表单 + 校验提示），不做拖拽。新建事项时可选自定义流程。同时提供 CLI 等价操作，便于测试。 | 验收要能在产品里走通 |

## 4. 用户场景

- S1 沿用内置模板：用户新建事项，选「软件开发」，和今天完全一样地推进到交付归档。
- S2 打开老事项：升级后打开升级前创建的事项（含进行中、已归档、已收起的），阶段名、记录、执行日志、交接、合并入口都和升级前一致，并能继续推进。
- S3 定制流程：项目负责人以「软件开发」为起点复制一份，删掉「交互设计」，在「测试验证」后加一个「安全审查」（Test 角色），保存为「后端开发」。
- S4 使用定制流程：新建事项选「后端开发」，阶段条显示 7 个阶段（产品需求、技术方案、开发实现、测试验证、安全审查、独立验收、交付归档），手动或自动运行能一路走到交付归档并合入。
- S5 跳过与退回：在定制流程里，产品需求阶段写 `AEP-SKIP: 技术方案：…`，技术方案被跳过；「安全审查」写 `AEP-BACK: 开发实现：…`，事项退回开发实现。
- S6 改流程不影响在途事项：负责人把「后端开发」再改名一个阶段或删除整套流程，已用它创建的事项仍按创建时的阶段显示和推进。
- S7 草稿生成：AI 起草事项（work_draft）时能列出并选用项目的自定义流程。

## 5. 范围

### 5.1 流程定义（F1）

一套流程包含：

- `id`：项目内唯一、创建后不变；内置三套保留现有标识 `Legacy`/`Software`/`Game`。
- `label`：显示名，项目内唯一。
- `stages`：有序列表，每个阶段包含
  - `name`：阶段名（AEP-SKIP / AEP-BACK 按它匹配）；
  - `brief`：阶段职责说明（写入交接文本）；
  - `role`：Plan / Build / Test / Accept / Deliver 之一，含义不变；
  - `skippable`：能否被 AEP-SKIP 或人工跳过；
  - `back_to`：本阶段可用 AEP-BACK 退回的阶段名列表；为空表示「之前的任意阶段」（即当前行为）。

### 5.2 内置模板（F2）

三套内置模板用 F1 表达，且等价于现状：`skippable` = 「下标 > 0 且 role == Plan」，`back_to` 为空。内置模板不可修改或删除，但可以「复制为新流程」。

### 5.3 项目自定义流程（F3）

在项目上新增、复制、编辑、删除自定义流程。保存前必须通过校验（见第 7 节）。

### 5.4 事项绑定（F4）

- 新建事项（Studio、CLI、导入、草稿）时选择流程；默认仍是当前的默认模板。
- 事项保存流程快照；事项的阶段条、阶段数、完成判断、退回、跳过、预算、配置都从快照读。
- 没有快照的旧事项从 `template` 解析为内置流程。

### 5.5 读取方改造（F5）

第 2 节列出的所有调用方改为读取「事项的流程」，不再直接调用 `Template::stages()` 或假设固定下标。凡是按 role 判断的逻辑（可写、门禁、固定 HEAD、默认 CLI、默认沙箱、门禁失败退回最近的 Build、交接说明）保持按 role 判断。

### 5.6 执行请求自包含（F6）

新写的 `request.json` 带上本次所用的阶段定义（至少当前阶段及整套阶段名/角色），执行器只看请求即可工作；旧的只带 `template` 的 `request.json` 仍能被时间线、证据、续聊读取。

### 5.7 Studio（F7）

- 项目设置里的流程列表与表单编辑器（列表 + 上移/下移/添加/删除，字段表单，即时校验提示，保存/取消）。
- 新建事项的流程选择里列出内置 + 项目自定义流程，显示阶段名预览。
- `studio/src/api/types.ts` 的 `Template` 从固定联合类型改为可容纳自定义 id。

## 6. 不做

- 可视化拖拽编排器。
- 并行阶段、条件分支、循环（除已有 AEP-SKIP / AEP-BACK）。
- 跨项目共享 / 导入导出流程、仓库内流程文件。
- 事项级临时增删阶段；进行中事项切换到另一套流程。
- 新增角色类型，或在流程里覆盖各角色的默认 CLI / 沙箱（仍可在事项上按阶段设置，与今天相同）。

## 7. 校验规则与边界情况

保存自定义流程时校验，失败给出指出具体阶段的中文错误，不保存：

- E1 至少 2 个阶段，最多 20 个。
- E2 阶段名去首尾空白后非空、不超过 20 个字符、流程内唯一；不得含换行、`：`、`:`、`「」<>`（否则 AEP-SKIP / AEP-BACK 无法解析）。
- E3 恰好一个 Deliver 阶段，且是最后一个。
- E4 `skippable` 只允许用于非首个的 Plan 阶段；Build、Test、Accept、Deliver 一律不可跳过（与现有「门禁不可跳过」一致）。
- E5 `back_to` 中每个名字必须是本阶段之前的阶段；首个阶段的 `back_to` 必须为空。
- E6 流程 `label` 非空、项目内唯一，不得与内置模板显示名重复。
- E7 存在 Build 阶段而其后、Deliver 之前没有 Accept 阶段时给出**警告**（合并使用独立验收固定的提交），允许保存——内置 Legacy 即是此结构，其合并行为保持现状。

运行期边界：

- E8 AEP-SKIP 写了不存在、在前面、或不可跳过的阶段名：忽略该行（现状行为）。
- E9 AEP-BACK 写了不在 `back_to` 允许范围内的阶段名：视为未退回，阶段按普通结果处理，并在证据中记录被拒绝的退回目标。
- E10 删除一套仍被事项引用的自定义流程：允许；已有事项靠快照继续；新建事项不再能选它。
- E11 事项快照损坏或缺失、`template` 也无法识别：事项可以打开并显示错误提示，不崩溃、不影响同项目其他事项。
- E12 旧事项 `stage` ≥ 阶段数（已完成 / 已收起）：仍判定为已完成。
- E13 编辑流程期间有事项正在执行：不受影响（快照已冻结）。
- E14 自动运行遇到 Test/Accept 失败：退回该阶段之前最近的 Build；没有 Build 时停在失败阶段等人处理（与现状一致）。

## 8. 验收标准

### 兼容性

- AC1 `cargo test --locked` 全部通过，含 `tests/autopilot.rs`、`tests/project_handoff.rs`，且这两份测试文件不改断言。
- AC2 三套内置模板经新定义解析后，阶段名、brief、role、可跳过性、默认 CLI、默认沙箱与改造前逐项一致（有一条单测逐项对比）。
- AC3 内置模板生成的交接文本（handoff）与改造前逐字一致（快照测试）。
- AC4 用改造前格式的项目数据（无流程快照、`template` 为 Legacy/Software/Game）加载：事项可打开、阶段条正确、可继续推进到下一阶段；已收起/已完成的事项仍显示为完成（有测试夹具）。
- AC5 改造前格式的 `request.json`（只有 `template` + `stage`）仍能被时间线、证据读取和续聊使用。

### 自定义流程

- AC6 通过 CLI 或 Studio 创建 S3 中的「后端开发」流程并保存成功；重启 Studio 后仍在。
- AC7 用「后端开发」新建事项，事项依次走过 7 个阶段到交付归档、可合入，过程中 `安全审查` 按 Test 角色运行（允许网络的默认沙箱、门禁、不能写文件）。有一条端到端测试（可用假执行器）覆盖。
- AC8 在该流程中：产品需求阶段输出 `AEP-SKIP: 技术方案：…` 后，技术方案被标记跳过；`AEP-SKIP: 安全审查：…` 被忽略（不可跳过）。
- AC9 `安全审查` 输出 `AEP-BACK: 开发实现：…` 时事项退回开发实现；若其 `back_to` 只允许「产品需求」，则同一输出不退回并在证据中记录（E9）。
- AC10 自动运行下 `安全审查` 失败时，自动退回「开发实现」（最近的 Build）。
- AC11 第 7 节 E1–E6 每条规则各有一个被拒绝的用例，错误信息指出具体阶段；E7 产生警告但可保存。
- AC12 修改或删除「后端开发」后，已用它创建的事项阶段名、阶段数、推进行为不变（S6）。
- AC13 新写的 `request.json` 包含本次阶段定义；执行器在仓库里没有该自定义流程定义时也能按请求完成该阶段。

### 代码结构

- AC14 `src/` 与 `studio/src-tauri/src/` 中，除流程定义模块本身外，不再有 `Template::stages()` 调用或对 `LEGACY/SOFTWARE/GAME` 的直接引用（可用 grep 核对）。

### Studio

- AC15 项目设置中可列出、复制、编辑、删除自定义流程；校验错误在保存前就地提示；内置模板只读。
- AC16 新建事项时可选自定义流程并看到阶段名预览；事项页阶段条按其流程显示。
- AC17 `pnpm`/`npm` 的前端类型检查与构建通过（以仓库现有 studio 脚本为准）。

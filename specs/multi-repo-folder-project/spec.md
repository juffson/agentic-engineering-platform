# 项目 · 从多仓库文件夹创建项目 — 产品需求

事项：e75f169e0a4246c4a633ab58e56ef786
本阶段 run：`eb9c9e79dcf64b058a1b84b9bb1ea41b`

## 1. 背景与现状

团队常把一组相关仓库放在同一个「工作区」文件夹下。这个文件夹本身不是 git 仓库，只在顶层放一份团队约定（AGENTS.md / CLAUDE.md）。例如 `/Users/sirius/Desktop/cowork/market-data/03-行情基础数据计算存储`：顶层只有 AGENTS.md，下面有 11 个独立 git 仓库（genki、genki-api、genki-core、genki-kline、genki-snapshot、genki-storage、history-loader、quote-backup、quote-data、quote-data-service、quote-trade）。

现在用这个文件夹新建项目会报错「不是 Git 仓库: git rev-parse: fatal: not a git repository」。用户只能逐个选 11 次子仓库，而且工作区顶层的 AGENTS.md 不会进入任何阶段。

相关代码（供技术方案参考，本阶段不改）：

- `Workspace::open`（`src/workspace.rs:97`）：用 `git rev-parse --show-toplevel` 定位仓库根，不是仓库就报错。
- Studio：`api::repository`（`studio/src-tauri/src/api.rs:266`）在 `Workspace::open` 的错误外面加上「不是 Git 仓库」，`create_project`（:272）和 `add_repository`（:340）都经过它。`pick_folder`（:316）选到仓库内的子文件夹时会解析成仓库根，选到非仓库时原样返回。
- CLI：`project create --repository <path>...` 和 `project add-repo <path>`（`src/project_cli.rs:784`、:823）都经过 `root()`（:379），也就是 `Workspace::open`。
- 前端：新建项目对话框（`studio/src/components/Dialogs.tsx` 约 :320–:420）选完文件夹后对每个路径调用 `importScan`，查找可导入的记忆和分支。仓库页「添加仓库」（`studio/src/components/SecondaryPages.tsx:430`）是一个路径输入框加「选择文件夹…」。
- `Project`（`src/project.rs:459`）里只有 `repositories: Vec<PathBuf>`，没有工作区根的概念。
- 阶段 prompt 由 `handoff::header` / `memory_body`（`src/handoff.rs:81`）和 `workflow_stage::context`（`src/workflow_stage.rs:155`）拼出。Claude 阶段的 cwd 是 `<catalog>/worktrees/...` 下的事项工作树，可访问目录只有工作树、`--add-dir` 加入的执行目录和 receipt 目录，再加上对 runs 目录的 `Read(//…/**)` 授权（`src/workflow_stage.rs:1215-1232`）。工作区根不在这些目录里。另外，工作树不在工作区根下面，Claude Code 也不会自动从上级目录加载工作区根的 CLAUDE.md。

## 2. 用户场景

- **S1 从工作区文件夹新建项目**：用户在「新建项目」里选择 `03-行情基础数据计算存储`。对话框列出找到的 11 个仓库，默认全选。用户点「创建项目」后，项目包含这 11 个仓库，项目名默认填文件夹名。
- **S2 只要其中几个仓库**：同 S1，用户取消勾选 quote-backup、history-loader，创建后项目只有剩下的 9 个仓库。
- **S3 选错文件夹**：用户选了一个不是仓库、子目录里也没有仓库的文件夹（如「下载」里的资料目录）。界面明确提示「这个文件夹和它的子目录里没有 git 仓库」，不创建项目，也不显示 git 原始报错。
- **S4 普通单仓库**：用户选一个普通 git 仓库（或仓库里的子文件夹）。行为和现在完全一致：不出现勾选清单，照常扫描可导入的记忆和分支。
- **S5 给已有项目补仓库**：项目已经有 genki、genki-api。用户在仓库页「添加仓库」选择工作区文件夹，看到清单：已在项目里的两个显示为「已添加」且不可勾选，其余默认勾选，一次添加。
- **S6 阶段读取团队约定**：项目记住了工作区根。之后任一阶段的 prompt 里都有一行，写明工作区根的 AGENTS.md / CLAUDE.md 路径并要求先读。阶段 Agent 能直接读到这些文件，prompt 里不嵌入文件内容。
- **S7 CLI 批量添加**：用户在终端执行 `aep project create 行情 --repository <工作区>`。不带 `--all` 时，命令列出找到的仓库，提示加 `--all` 全部添加或逐个用 `--repository` 指定，不创建项目、返回非零。带 `--all` 时，命令把全部仓库加进项目并记录工作区根。`project add-repo <工作区> [--all]` 的行为相同。
- **S8 多仓库事项**：在 S1 建好的项目里新建事项，仍然用现有的仓库选择交互选其中一个或多个仓库。每个选中的仓库各自建工作区和 `aep-stage` 分支，各自交付，互不影响。

## 3. 范围

### 包含

**发现仓库**

- **R1**：路径本身（或它的上级）是 git 仓库时，行为不变，按现有逻辑解析到仓库根。
- **R2**：路径存在、是目录，但不在任何 git 仓库里时，扫描它的子目录，找出其中的 git 仓库：
  - 默认深度 2 层，即 `<root>/a` 和 `<root>/a/b`；
  - 跳过 `node_modules`、`target` 和所有以 `.` 开头的目录；
  - 找到一个仓库后不再进入它的内部（仓库内部的嵌套仓库或 submodule 由该仓库自己管理）；
  - 结果按相对路径排序，每项给出绝对路径（规范化后）、相对工作区根的路径和目录名。
- **R3**：扫描结果为空时，返回固定提示「这个文件夹和它的子目录里没有 git 仓库」（可以附上扫描深度说明），不显示 git 原始报错。
- **R4**：路径不存在或不是目录时，提示「路径不存在」或「不是文件夹」，不扫描。

**Studio 界面**

- **R5**：新建项目对话框里，选择或填入的路径命中 R2 时，显示「在 <文件夹> 下找到 N 个 git 仓库」的勾选清单，默认全选，支持单个取消、全选和全不选。创建时只添加勾选的仓库；全部取消时「创建项目」不可用，或提示至少选一个仓库。
- **R6**：仓库页「添加仓库」命中 R2 时显示同样的清单。已在项目中的仓库标为「已添加」，不可勾选，也不计入待添加数量。确认后一次添加勾选的仓库；如果全部已添加，提示「这些仓库都已在项目里」。
- **R7**：从工作区文件夹展开出的仓库，按现有逻辑逐个做「可导入的记忆和分支」扫描，导入区按仓库分组展示。扫描进行中「创建项目」的行为与现在一致。导入区在仓库很多时的展示方式（折叠、只展示有内容的仓库）由交互设计决定。
- **R8**：项目名为空时，默认填工作区文件夹名（与现在选单个仓库时取文件夹名一致）。

**工作区根**

- **R9**：`Project` 新增可选字段「工作区根」（`workspace_root`，可选路径）。旧项目数据没有这个字段，必须能照常读写，序列化时为空则不写出。
- **R10**：以下操作会设置工作区根：
  - 用工作区文件夹新建项目（无论勾选几个仓库）；
  - 已有项目还没有工作区根时，通过「添加仓库」或 `add-repo` 用工作区文件夹添加。
  
  项目已有工作区根、又用另一个工作区文件夹添加仓库时，只添加仓库，不覆盖原工作区根，并在界面或 CLI 输出里说明（是否支持多个工作区根见 §6 Q3）。
- **R11**：仓库页显示当前工作区根路径，以及顶层找到的说明文件（AGENTS.md / CLAUDE.md，有哪个列哪个）。本事项不要求在界面上修改或清除工作区根（见 §6 Q4）。

**阶段 prompt**

- **R12**：项目有工作区根，且顶层存在 AGENTS.md 和/或 CLAUDE.md 时，每个阶段 prompt 加一行固定文字，例如「项目工作区说明：开始前先读 <root>/AGENTS.md（、<root>/CLAUDE.md），这是团队对该组仓库的约定」。只写路径，不嵌入内容。两个文件都不存在时不加这一行。
- **R13**：Claude 阶段在所有沙箱档位下都能用 Read 读到 R12 列出的文件，方式参照现有 runs 目录的 `Read(//…)` 授权，不需要人工审批。授权只覆盖这几个文件（或工作区根的只读访问，由技术方案决定），不能因此获得工作区根的写权限。Codex、ZCode 阶段也要能读到；做不到的客户端要在技术方案里写明，并在 prompt 里保持同样的引用。
- **R14**：这一行不计入项目记忆和仓库记忆的截断额度，也不影响现有交接、记忆的拼接顺序。按 stage-token-diet 的约定，续接（`since` 有值）时不重复注入。

**CLI**

- **R15**：`project create --repository <path>` 中，任何一个 path 命中 R2 时：
  - 不带 `--all`：列出找到的仓库（相对路径和绝对路径），提示「加 --all 全部添加，或用 --repository 逐个指定」，不创建项目，退出码非零；
  - 带 `--all`：把找到的全部仓库加入，与其他 `--repository` 合并去重，并按 R10 记录工作区根；
  - 一个仓库都没找到：输出 R3 的提示，退出码非零。
- **R16**：`project add-repo <path> [--all]` 的规则同 R15。带 `--all` 时跳过已关联的仓库，输出新增和已存在的仓库列表。现有「选中事项时同时把仓库加入事项」的行为（`work.include`）对展开后的每个仓库都生效。
- **R17**：普通仓库路径传入 `--all` 时，`--all` 不产生任何效果，行为与现在一致。

**事项与交付（回归）**

- **R18**：事项创建时的仓库选择交互、每个仓库各自的工作区和 `aep-stage` 分支、各自的远端与交付配置都保持不变。工作区根不是仓库：不建工作区，不出现在事项的仓库选择里，也不参与交付。

### 不包含

- 不支持把完全没有 git 的普通文件夹当作仓库。阶段依赖工作区分支和提交，是否另开事项待定。
- 不自动给子仓库配置远端，仍在仓库页「远端与交付」逐个设置。
- 不把工作区根的 AGENTS.md / CLAUDE.md 内容复制进 prompt 或项目记忆。
- 不在「导入 / 同步」时自动发现工作区根下新增的仓库，本事项只记录待确认（§6 Q2）。
- 不改变 `pick_folder` 对「仓库内子文件夹解析为仓库根」的行为。

## 4. 边界情况

- **E1 选的是仓库内部的子文件夹**：`rev-parse --show-toplevel` 会解析到外层仓库，不进入扫描（R1）。哪怕这个子文件夹下还有独立的嵌套仓库，也按外层仓库处理。这是现状，不做改变。
- **E2 工作区根本身是 git 仓库，子目录里也有仓库**：按 R1 当作单个仓库处理，不扫描子目录。
- **E3 子目录是 worktree 或 submodule（`.git` 是文件而不是目录）**：worktree 识别为仓库，规范化到它自己的根。submodule 只会出现在某个仓库内部，按 R2 不会被扫到。识别方式（看 `.git` 是否存在，或对候选目录跑 `rev-parse`）由技术方案决定，但结果必须和「对该目录执行 `Workspace::open` 能成功」一致。
- **E4 裸仓库（`*.git` 目录，没有工作树）**：不算仓库，不列出。阶段需要工作树。
- **E5 符号链接**：子目录是指向工作区外部仓库的符号链接时，按规范化后的真实路径列出。多个链接指向同一仓库时去重。链接循环不能导致扫描卡死，深度上限本身就能保证这一点。
- **E6 超过 2 层的仓库**：默认扫不到。清单下方提示「只查找了 2 层子目录」，让用户知道可能有遗漏。是否允许调整深度见 §6 Q1。
- **E7 子目录数量很多或有无权限的目录**：读不了的目录直接跳过，不中断扫描，也不报错。扫描要有合理的上限（如目录数或耗时），超过上限时停止并提示结果可能不完整。具体数值由技术方案定。
- **E8 新建项目时混填**：文本框里一行是普通仓库，另一行是工作区文件夹，最终仓库集合是两者的并集，去重后创建。同一个仓库从两条路径都能得到时只加一次。
- **E9 多个工作区文件夹**：新建项目时填了两个都命中 R2 的文件夹，两份清单分别展示。工作区根取第一个（或由交互设计决定让用户选择），另一个只贡献仓库。是否支持多个工作区根见 §6 Q3。
- **E10 名称冲突**：不同子目录下有同名仓库（如 `a/api` 和 `b/api`）。清单以相对路径区分，项目中按绝对路径存储，不冲突。
- **E11 工作区根后来被移动或删除**：阶段 prompt 不再引用缺失的文件（R12 在运行时检查文件是否存在），不能让阶段失败。仓库页显示「工作区根不存在」。
- **E12 工作区根顶层只有 CLAUDE.md、只有 AGENTS.md，或两者都有**：分别引用存在的文件。两者都没有时记录工作区根，但 prompt 不加这一行（R12），仓库页显示「顶层没有说明文件」。
- **E13 子仓库自己也有 AGENTS.md / CLAUDE.md**：在事项工作树内，Agent 照常读取。工作区根的说明作为补充，两者都保留，本事项不处理二者冲突。
- **E14 并发**：用户在清单展示后、确认前，在文件系统里删除了某个子仓库。确认时对每个仓库重新校验（`Workspace::open`），失败的仓库要在错误里点名。整体是否全部回滚由技术方案定，但不能出现「部分仓库已添加却显示失败」而状态说不清的情况。
- **E15 Studio mock 与真实后端一致**：`studio/src/api/mock.ts` 要能模拟「多仓库文件夹」和「空文件夹」两种结果，供 Playwright 使用。
- **E16 已存在的项目数据**：没有 `workspace_root` 的旧项目，读写、阶段 prompt、所有现有测试的行为都不变。

## 6. 待确认

- **Q1 扫描深度**：默认 2 层能覆盖 03-行情基础数据计算存储。market-data 下其他工作区可能更深。可选方案：
  - (a) 固定 2 层，界面提示「只查找了 2 层」；
  - (b) 界面提供「查找更深」按钮，CLI 提供 `--depth N`；
  - (c) 默认 3 层。

  建议 (b)：默认 2 层，CLI 加 `--depth`，界面在结果为空或用户怀疑有遗漏时可以再查一层。由交互设计和技术方案定稿。
- **Q2 导入 / 同步时自动发现新仓库**：工作区根下新增的仓库，是否在「导入 / 同步」时提示加入。建议本事项不做，只在仓库页提供「重新扫描工作区根」入口（如果交互设计认为成本低），自动发现另开事项。
- **Q3 多个工作区根**：一个项目是否允许多个工作区根（来自不同文件夹）。建议本事项只支持一个，后来的只贡献仓库并给出提示（R10）。
- **Q4 修改或清除工作区根**：是否需要在仓库页修改或清除工作区根。建议本事项只读展示，清除留到后续。
- **Q5 读取授权范围**：R13 是只授权 AGENTS.md / CLAUDE.md 两个文件，还是授权整个工作区根只读。整个根只读更方便 Agent 顺着说明查看相邻仓库，但其他仓库的未提交内容也会暴露给阶段。由技术方案决定，倾向只授权说明文件。
